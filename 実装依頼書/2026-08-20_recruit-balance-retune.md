# 募集人数の変更に伴う 難易度 / XP の再調整(測ってから決める)

**ステータス**: 起草済(未承認)
**依存**: ⚠ **`2026-08-20_quest-recruit-size.md`(C)の完了が前提**
**撤退スイッチ**: なし(値の調整。撤退は `?recruit=0` で C ごと戻す)

---

## 目的

C でパーティ人数がクエストごとに変わった。**その結果どうなったかを実測し、値を決める。**

⚠ **この依頼書のゴールは「調整すること」ではなく「測ってから決めること」。**
測った結果「調整不要」も正式な結論として認める。

---

## 背景・現状

### C が持ち込んだ問題

| id | 旧 NPC 数 | 新 NPC 数 | 影響 |
|---|---|---|---|
| `goblin-mine`(★1・廃坑) | 3 | **1** | ⚠⚠ **最初のクエストが最も過酷になる** |
| `bandits-forest`(★2) | 3 | 2 | 難化 |
| `lizard-swamp`(★2) | 3 | 2 | 難化 |

ここが最難関になるのは出荷できない。

廃坑については **C とは無関係に** 難易度 / XP の再調整が保留になっている
(卓上グリッド P9 で寄り道 4 か所と宝箱を足した分の未調整)。**この依頼書で一緒に片付ける。**

## 測り方(ここが本体)

### 1. ペア比較でしか測れない

オートプレイは非決定論。**「新の数値」だけ見ても意味がない。**
同一ビルド・同一条件で `?recruit=0`(旧) と 既定(新) を**交互に**回し、対で比較する。

```
node tools/sweep_recruit_balance.js --scenario goblin-mine --pairs 20
  → 1 ペア = [?recruit=0 で 1 回] + [既定で 1 回]
```

### 2. 測る指標(実時間ではなくラウンド数)

⚠ **所要「秒数」で測らない。** マシン負荷とポーリング間隔で揺れる。**戦闘ラウンド数**で測る。

| 指標 | 取り方 |
|---|---|
| クリア率 | 完走 / 試行 |
| 主人公の死亡率 | 主人公が落ちた回数 / 試行 |
| NPC の死亡数(平均) | 1 走行あたり |
| ボス戦のラウンド数(中央値) | ボス出現〜撃破 |
| 総獲得 XP(中央値) | 走行終了時 |

### 3. 試行回数

⚠ 過去に「±1 体の護衛調整は N=60 でもノイズ以下」だった実績がある。
**小さな差を追わない。** 各シナリオ **N ≥ 20 ペア**を回し、
それでも差が見えないものは「**この変更はこのシナリオに影響しなかった**」と結論して**触らない**。

### 4. スイープ中の禁止事項

- ⚠⚠ **スイープ中に `tavern.html` / `index.html` を編集しない。** 前半と後半で別ビルドの混合物になる
- ⚠⚠ background で回す場合、**`TaskStop` では止まらない**(bash ループと node が生き残る)。
  実測して殺すこと。出力は**毎回新しいファイル名**に書く(混線防止)
- `?autoplay=N` は N 倍速。ただし **`=1` だけ 5 倍**という例外がある。既存ドライバは 30 / 25 を使っている

## 調整の順序(この順を守ること)

### 1. まず測る(調整しない)

上記のペア比較を 6 シナリオ + 闇市生成クエストで回し、**表にしてユーザーへ報告する**。
**ここで一度止まる。** 何をどう動かすかはユーザーの判断を仰ぐ。

### 2. 敵の「質と配置」で調整する(数ではない)

⚠ **このプロジェクトでは「敵を増やす / 減らす」がバランスに効かないことが実測で分かっている。**
効くのは**敵の種類・配置・ボスのロジック**。

調整の候補(効き目の大きい順):

1. `recruit:` の個別上書き — **最も安全。** 廃坑だけ `recruit: 3` にすれば元に戻る
2. 敵の構成(エリート個体の有無・遠距離役の数)
3. 湧き位置・寄り道スポットの配置
4. ボスのロジック(HP ではなく行動)

### 3. XP は最後

XP テーブルは D&D 3.5 準拠(累積 XP = `500 × Lv × (Lv-1)`、Lv10 = 45,000、
6 シナリオ + 最終 2 周で Lv10 到達想定)。**ここを動かすと全シナリオの設計前提が動く。**

⚠ **先に確かめること**: パーティ人数が減った時、獲得 XP が
「**1 人あたり増える**」のか「**総量が同じで頭割りされない**」のかを**コードで確認する**。
ここが分からないまま XP を触らない。

## 受入条件

1. **測定結果の表がユーザーに報告されている**(6 シナリオ + 生成クエスト、N ≥ 20 ペア、5 指標)
2. 各シナリオについて「調整した / 調整不要と判断した」のどちらかが**理由付きで**記録されている
3. 調整したシナリオについて、**調整後にもう一度ペア比較を回して**、狙った方向に動いたことを示している
4. `goblin-mine` の主人公死亡率が、**旧(NPC 3 人)と同等以下**になっている
   初見が最初に触る場所なので、ここだけは「同等以下」を条件にする
5. 既存 golden ドライバ群が全部緑(または赤の理由が 1 本ずつ書かれている)

## リスクと対策

| リスク | 対策 |
|---|---|
| 差がノイズに埋もれて何も言えない | N ≥ 20 ペア。それでも見えなければ「**影響しなかった**」を結論として書く。無理に動かさない |
| 調整が過剰になり全部やさしくなる | 1. で止まってユーザー判断を仰ぐ。**測る前に触らない** |
| スイープ中の編集で混合物ができる | スイープ開始前に作業ツリーを固定。走行中は一切編集しない |
| background スイープが残留して次の測定を汚す | 出力は毎回新ファイル。終了後に**プロセスを実測して殺す** |
| XP を動かして全シナリオが崩れる | 3. は最後。かつ「XP が頭割りかどうか」をコードで確認してから |
