### 0-1 なぜ `?recruit=0` が空振りするのか

人数を決める `isRecruitOn()` / `recruitCountOf()` は **`tavern.html` にしかない**。
`index.html` は `sessionStorage["dragonfighters.partyMembers"]` を読むだけで、
無ければ `orderFormation(buildParty(heroOld))` = `PARTY_SIZE`(定数 4)へ**無言でフォールバック**する。

既存のヘッドレスドライバは全部 `index.html` を直起動する:

- `tools/auto_debug_run.js` — `index.html?autodebug=N&autoplay=...`
- `tools/probe_n4_stall.js` — `index.html?autoplay=...&diag=1`

→ URL に `recruit=0` を足しても `index.html` の誰も読まない。実測:

```
A: index直起動 (既存ドライバ)      allies=3 (計4人)  ss=null
B: index直起動 + ?recruit=0        allies=3 (計4人)  ss=null   ← A と同じ
```

⚠ `tools/verify_recruit_size.js`(#7 の検証・79/79)は **`tavern.html` だけ**を駆動し、
`index.html` への遷移を**横取りで abort** している。つまり
**人数を減らした状態でダンジョンを 1 回もプレイしていない。**

### 0-2 正しい測定台 = 酒場を本番どおり通して遷移させる(実測で成立)

`departToScenario()` は `tavern.html` の URL から `autoplay` を読んで
`index.html?autoplay=N` へ引き継ぐ。だから **酒場側に `?recruit=0` を付ければ腕が本当に割れる**。

```
tavern.html?autoplay=15&recruit=0   → prepScenario=sc; regeneratePartyMembers(); departToScenario()
                                    → index.html?autoplay=15  (遷移は横取りしない)
```

実測(シナリオ2・各腕 1 走行):

```
OLD (?recruit=0)  酒場: recruitOn=false  recruitCountOf=2 → index側 allies=3 (計4人) 仲間Lv=[1,1,1]
NEW (既定)        酒場: recruitOn=true   recruitCountOf=2 → index側 allies=2 (計3人) 仲間Lv=[1,1]
```

⭐⭐⭐ **この経路でなければならない理由**: `sessionStorage` へ手作りの `partyMembers` を
注入する案でも人数は作れる。しかし仲間の **Lv は `assignCompanionLevels()`、装備は `allyEquip`** が
決めており、手作りでは本番と別物になる。**人数だけ合った偽の編成で難易度を測ることになる。**

⚠⚠ しかも手作り注入は**無言で失敗する**。実測で `classKey:"wizard"`(本番の `PARTY_ZONES` に無い)を
1 つ混ぜたら、index 側の `pm.every(m => PARTY_ZONES[m.classKey])` が false になり
**formation ごと捨てられて 4 人に戻った**のに、人数だけ見ると「旧仕様どおり」に見えて緑になった。

### 0-3 前回窓の「4 試行中 3 回全滅」は #7 のせいではない

あの 4 試行は `tools/probe_n4_stall.js`(= `index.html` 直起動)で採った。
`partyMembers` を仕込んでいないので **全部が計 4 人 = 旧仕様の編成**だった。

⭐⭐⭐ つまり **シナリオ2 は #7 以前から 4 人でも全滅する**。#7 はそこへ上乗せするだけ。
「C(#7) が持ち込んだ問題」という旧本文の枠組みは、少なくともシナリオ2 については誤り。
**既存の難易度と #7 の上乗せを分けて測る**(§3-3 の腕はそのために 2 本ある)。

### 0-4 XP は頭割りされない(旧本文「先に確かめること」への答え)

`gainXP(amount, source)` は主人公の `currentTotalXp` / `earnedXpThisRun` に足すだけ。
パーティ人数で割る処理はどこにも無い。呼び口は 4 箇所だけ:

| 場所 | 内容 |
|---|---|
| `index.html` の敵撃破処理 | `gainXP(enemy.def.xp \|\| 0, nm)` |
| 罠解除 ×2 | `gainXP(spec.disarmXP, "罠解除")` |
| クリア報酬 | `gainXP(clearXp, "クリア報酬")` |

⭐ **人数は XP 量に一切影響しない。** クリアできれば同額、できなければゼロ。
→ **XP の調整は人数問題と切り離してよい**(残るのは §2 の宿題 2 = 廃坑の既存宿題だけ)。

## 3. 測り方(全面改訂)

### 3-1 測定台 — 新規 `tools/sweep_recruit_balance.js`

⛔ **既存の `auto_debug_run.js` / `probe_n4_stall.js` を流用しない**(§0-1 の理由で腕が割れない)。

1 走行の手順:

1. `evaluateOnNewDocument` で `dragonfighters.*` / `df.*` を purge し、
   `dragonfighters.prologueSeen = "1"` を焼く(前口上は測定対象外)
2. `tavern.html?autoplay=<N>` (+ OLD 腕だけ `&recruit=0`) を開く
3. **本番の関数だけ**を呼ぶ(写経しない):
   `prepScenario = scenarios.find(s => s.id === <id>)` → `regeneratePartyMembers()` → `departToScenario()`
4. **遷移は横取りしない。** `index.html?autoplay=<N>` へ着地するのを
   `typeof mapData !== 'undefined' && typeof heroAI === 'function'` で待つ
5. 1 秒間隔でポーリングして走行を観測(⭐ 150ms の evaluate は測定対象そのものを遅くする = P9 の教訓)

### 3-2 装置 assert(これが無いと全部緑になる)

1 走行ごとに必ず記録し、1 つでも崩れた走行は**集計から外して件数を報告する**:

| 装置 assert | 崩れると何が起きるか |
|---|---|
| 酒場側の `isRecruitOn()` が腕どおり(OLD=false / NEW=true) | 腕が割れていないのに数字が出る |
| 酒場側の `recruitCountOf(sc)` が期待値 | ★の読み違いに気づけない |
| 着地 URL が `/index.html` を含む | 遷移していないのに「走った」ことになる |
| index 側の `allies.length + 1` が期待人数 | フォールバックした 4 人を新仕様として数える |
| index 側の `scenarioId` が対象シナリオ | 別のシナリオを測る |

⚠ **母集団ガード**: 「両腕とも N 走行を集計できたか」を最後に 1 行出す。
0 件でも「差が無かった」に見えるので、**件数を出さない集計は禁止**。

### 3-3 腕(2 本)

| 腕 | URL | 意味 |
|---|---|---|
| OLD | `tavern.html?autoplay=N&recruit=0` | #7 以前(NPC 3 = 計 4 人)。**§2 の宿題 2・3 だけが乗った状態** |
| NEW | `tavern.html?autoplay=N` | #7 以後(★の数)。**宿題 1 が上乗せされた状態** |

⭐ 2 本を**交互に**回す(同一ビルド・同一マシン負荷で対にする)。
⭐ **OLD 腕そのものが「既存の難易度」の測定値**になる。ここが既に悪ければ #7 とは別の話。

### 3-4 指標

⚠ **所要「秒数」で測らない**(マシン負荷とポーリング間隔で揺れる)。

| 指標 | 取り方(裸の識別子で読む) |
|---|---|
| クリア率 | `dungeonCleared` が true で終わった走行 / 全走行 |
| 全滅率 | `gameOver` が true で終わった走行 / 全走行 |
| 到達ノード | 終了時の `currentNodeId`(**どこで折れたか**が本体。シナリオ2 は n1 / n4 で割れる) |
| 仲間の生存 | 終了時の `allies.filter(a => a.hp > 0).length` / `allies.length` |
| 獲得 XP(中央値) | `earnedXpThisRun` |
| 主人公 HP | 裸の `hp`(⚠ `playerHp` という識別子は**存在しない**。実測で `null` を踏んだ) |

### 3-5 規模(ユーザー決定 2026-08-23)

**シナリオ2 `bandits-forest` と 廃坑 `goblin-mine` の 2 本に絞る。各 N = 20 ペア。**

⭐ 残り 4 本(沼・砦・神殿・竜巣)を測らない理由:

- `lizard-swamp` は ★2 で 3→2 だが、シナリオ2 と同じ変化量。まず 2 本で効き目を見てから判断する
- `orc-fort` / `undead-temple` / `dragon-lair` は **#7 で人数が変わらない**(★3 以上 → clamp で 3 のまま)
  → **宿題 1 の影響が原理的にゼロ**。測っても差は出ない
- 闇市の生成クエストは `difficulty` を持たず fallback 3 で**これも人数不変**

⚠ 1 走行の実測レンジは **17〜206 秒**(全滅は速い)。2 本 × 20 ペア × 2 腕 = 80 走行。
並列ページを使ってよいが、**ポートは腕ごとに別**にする(⚠ 同時実行のポート衝突は偽の赤を生む)。

### 3-6 スイープ中の禁止事項

- ⚠⚠ **スイープ中に `tavern.html` / `index.html` を編集しない。** 前半と後半で別ビルドの混合物になる
- ⚠⚠ background で回す場合 **`TaskStop` では止まらない**(bash ループと node が生き残る)。
  実測して殺すこと。出力は**毎回新しいファイル名**に書く
- ⚠ 別窓が **#12 港町マップ**を並行進行中。`tools/make_grid_map.py` / `assets/town_phlan.jpg` に触らない。
  `git add .` 禁止 → **ファイル単位で add** し `git show :<path>` でステージを読んでから commit

### 3-7 読み取りに使う裸の識別子(実測済)

⭐⭐⭐ `window.<名前>` では読めない(classic script 直下の `let` は window に載らない)。
`page.evaluate` の中で**裸の識別子**として読む: `allies` / `partyComposition` / `scenarioId` /
`currentNodeId` / `gameOver` / `dungeonCleared` / `hp` / `earnedXpThisRun` / `PARTY_SIZE`。
酒場側は `scenarios` / `prepScenario` / `regeneratePartyMembers` / `departToScenario` /
`isRecruitOn` / `recruitCountOf`。

## 4. 調整の順序(この順を守ること)

### 1. まず測る(調整しない)

§3 のペア比較を 2 本回し、**表にしてユーザーへ報告する**。
**ここで一度止まる。** 何をどう動かすかはユーザーの判断を仰ぐ。

### 2. 敵の「質と配置」で調整する(数ではない)

⚠ **このプロジェクトでは「敵を増やす / 減らす」がバランスに効かないことが実測で分かっている**
(`±1 体の護衛調整は N=60 でもノイズ以下` — シナリオ3 の実測)。
効くのは**敵の種類・配置・ボスのロジック**。

調整の候補(効き目の大きい順):

1. `recruit:` の個別上書き — **最も安全。** 廃坑だけ `recruit: 3` にすれば元に戻る
2. 敵の構成(エリート個体の有無・遠距離役の数)
3. 湧き位置・寄り道スポットの配置
4. ボスのロジック(HP ではなく行動)

⚠ シナリオ2 は **n1 と n4 で折れている**(実測)。ボス部屋 n7 の調整では届かない可能性が高い。
**どのノードで折れたか**を見てから触る場所を決める。

### 3. XP は最後

§0-4 で「頭割りされない」ことが確定したので、**人数を理由に XP を動かす根拠は無い**。
動かすとしたら §2 の宿題 2(廃坑に寄り道 4 か所と宝箱が増えたぶん)だけ。

XP テーブルは D&D 3.5 準拠(累積 XP = `500 × Lv × (Lv-1)`、Lv10 = 45,000、
6 シナリオ + 最終 2 周で Lv10 到達想定)。**ここを動かすと全シナリオの設計前提が動く。**
実物は `index.html` の `XP_THRESHOLDS = [0, 1000, 3000, 6000, 10000, 15000, 21000, 28000, 36000, 45000]`。
