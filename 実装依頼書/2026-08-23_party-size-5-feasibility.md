# パーティ 5 人以上の可否調査

**ステータス**: **承認済** (2026-08-23)
**種別**: **調査チケット**。本番の挙動は変えない。成果物は「測った数値」と「サイズごとの可否判定」。

---

## 目的

`recruitCountOf()` の clamp 上限 3 (= パーティ 4 人) を **将来外せるかどうか** を、
engine を実測して判定する。**外すこと自体は目的ではない。**

判定は 1 つの ○× ではなく **サイズごと** に出す:

- **5 人** (主人公 1 + NPC 4) は行けるか
- **6 人** (主人公 1 + NPC 5) は行けるか
- 行けないなら、**何を直せば行けるか** を箇条書きで残す

⭐ **「上限 3 のままが正しい」も正式な結論。** この調査は上限を上げるための地ならしではない。
⭐ 出発点は `tavern.html:3270` の「5人以上を試したくなったら **別の調査チケット** を切ること」という
コード側からの名指しの指示。本チケットがその調査チケット。

---

## 背景・現状

- 人数を決めているのは `recruitCountOf()` ただ 1 本 (`tavern.html:3273`)。
  `const MIN = 1, MAX = 3` (`tavern.html:3274`) → `Math.max(MIN, Math.min(MAX, n))` (`tavern.html:3284`)。
- 実際に formation を作るのは `regeneratePartyMembers()` (`tavern.html:4595`)。
  `let partySize = PARTY_SIZE` → 募集 ON なら `1 + recruitCountOf(prepScenario)` (`tavern.html:4602-4603`)
  → `orderFormation(buildParty(heroKey, partySize))` (`tavern.html:4604`)。
- 出来た formation は `sessionStorage["dragonfighters.partyMembers"]` で index へ渡る
  (読み口 = `index.html:31537`)。**index は人数を自分で決めていない**。
- ★4 の `dragon-lair` でも NPC は 3 人で頭打ち = 最難関でもパーティ 4 人のまま、という設計上の宿題が残っている。

### ⚠ ただし「4 人前提」の根拠として書かれている 4 点は、大半が現在のコードでは成立していない

`tavern.html:3266-3270` は上限を外すなという警告と、その理由 4 点を列挙している。
**起草時 (2026-08-23) に本番の関数で 1 つずつ測ったところ、4 点のうち 3 点は既に事実と違っていた。**

`tavern.html` の「一度も通していない」と **2 つのコメントが食い違っている**。
どちらも実測ではないので、**どちらも根拠に使わない**。

### 本命のリスク = カメラの bbox クランプ

- `computeCameraTarget()` (`index.html:6273`) は隊列 (先頭 + 生存仲間、戦闘中は交戦敵も) の
  bbox にカメラをクランプする (`index.html:6297-6338`)。
- **bbox が画面より大きいとクランプ区間が空になり、「bbox 中央寄せ」に落ちる**
  (`loCx <= hiCx` が偽の枝、`index.html:6333-6334`)。
- ⚠⚠ これは机上の心配ではなく **過去に一度踏んでいる**。`index.html:31494-31497` に
  「隊列 bbox が 21 タイル幅 → 画面 (13 タイル) に収まらず … カメラが恒久未探索の黒い岩盤へ振られる」
  と、味方の初期配置を絶対座標から相対オフセットへ作り替えた理由として記録されている。
- ⭐ **スマホ (compact) は 4 人の時点で既に区間が空**。`index.html:6339-6347` のコメントが
  「味方 4 + 交戦敵で常にそれより大きいので『区間が空 → bbox 中央寄せ』に落ち」と明記し、
  実測値 **主人公が画面外のフレーム率 25.9%(廃坑) / 16.5%(竜の巣) / desktop 1280 は 0%** を残している。
  救済の `[compact-hero-anchor]` 節 (`index.html:6354-6368`) は
  **bbox を「主人公と行動キャラの 2 点」に絞る人数非依存のハードクランプ**なので、人数が増えても効き方は変わらない。
- ⛔ **したがって危ないのは desktop**。desktop は今 0% = 区間がまだ成立している。
  5 人目が bbox を広げて区間が空へ落ちるなら、**それが上限を上げられない唯一の理由**になる。
- 併せて見るべき近傍: `MAX_LAG = 480` (`index.html:16840`。これを超えて離れた仲間がいると `heroAI` が待つ) と
  置き去り仲間のワープ救済 (`index.html:16934`。`r<=3` で最大 ≈407px < 480 `:16951`)。
  人数が増えると隊列が伸びる = 待ちとワープの発動率が上がる可能性がある。

### ⚠⚠⚠ 測定道具は「在ることになっているが、無い」

- `index.html:6352` は「既存のカメラ回帰 (driver_camera)」と書いているが、
  **`tools/` に `driver_camera*.js` は 1 本も無い**(実測: `ls tools/ | grep -i camera` が空)。
- 検証シームとして用意されている `window.__camAnchorOff` (`index.html:6353`) を
  **使っている道具も 0 件**(実測: `grep -rn "__camAnchorOff" tools/*.js` が空)。
- フレーム時間を測るシーム (`__perf` / `frameMs` 等) も index.html には**無い**
  (`frameMs` のヒットはスプライトのアニメ再生尺であって計測ではない)。

→ **カメラとフレームの測定装置は、このチケットで新規に作る**。「既存の回帰があるはず」で流さないこと。

### ⭐ 測定台は #8 の物を使い回す (作り直さない)

`tools/sweep_recruit_balance.js` が既に **「酒場を本番どおり通して `departToScenario()` へ遷移させる」**
測定台を持っている:

- `tavern.html?autoplay=N` を開く (`tools/sweep_recruit_balance.js:210`)
- `prepScenario` を差して `regeneratePartyMembers()` → `departToScenario()` (`:163`)
- index 側で二重起動しないための guard (`:198`)

⛔⛔ **index.html を直接開く測定台を作らないこと。** `isRecruitOn()` / `recruitCountOf()` は

(#8 が実際にこれで 1 回転してから気づいた)。

## STEP 構成 (dev-loop 4 項目)

### STEP1 — 調査シームと測定装置の骨組み

1. `tavern.html` に `devPartySizeOverride(n)` を足し、`regeneratePartyMembers()` の
   `partySize` 決定の**直後**に 1 行だけ挟む。

   ```
   let partySize = PARTY_SIZE;
   if (isRecruitOn() && prepScenario) partySize = 1 + recruitCountOf(prepScenario);
   partySize = devPartySizeOverride(partySize);   // ← 調査シーム。?party 無しでは恒等
   ```

2. `devPartySizeOverride` の作法:
   - `?party=N` を読む。`N` が 2〜8 の整数**でなければ、引数をそのまま返す**。
   - ⚠⚠ **silent fail-open を作らないこと**。読めなかった / 範囲外だったときは
     `console.log("[DIAG] party override: ignored ...")` を**必ず 1 行**出す
     (`recruitCountOf` の `[DIAG]` `tavern.html:3281` と同じ作法)。黙って 4 に戻ると
     「シームが効いていないのに緑」という偽の緑が出る。
   - `location.search` を**毎回読む**。モジュール直下の `const` にしない
     (`tavern.html:3255-3257` が記録している TDZ の罠と同じ)。

3. `tools/probe_party_size.js` を新規作成。腕の起動は `sweep_recruit_balance.js:99-215` を流用する。
   この STEP では**空セクションと受入条件 1〜3 だけ**を通す。

**この STEP の受入条件**: 1. / 2. / 3.

## 受入条件

実装窓が自分で「終わった」と判定できること。装置は `node tools/probe_party_size.js`。

1. **既定が本番と 1 ビットも変わらない** — `?party` を付けない腕で、6 シナリオすべての
   formation 人数が #7 と一致する。既存 `node tools/verify_recruit_size.js` が **79/79 のまま緑**。
2. **負のコントロールを道具に内蔵** — `--negative` を付けると
   「シームが恒等でなくなった」ことを検出する assert が**赤くなる**。緑のままなら **exit 1**。
   ⭐ 「赤くなるはず」を人間の目視に委ねない。道具自身が判定して落ちること。
3. **母集団ガード** — 各走行が「本当に N 人で出発した」ことを、`departToScenario()` 後の
   `sessionStorage["dragonfighters.partyMembers"]` の実体の長さで確認する。
   ⚠⚠⚠ **届かなかった走行を成功に数えないこと。** 「違反 0 件」は、母集団が 0 でも 0 件になる
   (2026-08-23 に `?doors=0` の腕が対象ノードへ一度も到達せず、空振りを緑と読み違えた)。
   到達数を必ずログの先頭に出す。
4. **スポーン** — N=5 と N=6 で、6 シナリオ × 全ノードにわたり
   (a) 全員が互いに別タイル (b) `isTileWall(tx,ty)` が全員 false
   (c) **最終手段の「頭に重ねる」枝 (`index.html:31531`) に落ちた仲間が 0 人**。
   ⭐ (c) が 1 人でも出たノードは座標を全部ログに残す(そのノードが上限の真の制約)。
5. **隊列** — N=5 / N=6 で `orderFormation` の出力が front→mid→rear を守り、`[0]` が front zone。
   zone が 1 つも欠けていない (`buildParty` の (1) 各 zone 最低 1 人 `tavern.html:3293-3303` が効いている)。
6. **下部 HP ミニバーの枠** — 390x844 (compact) で `#hpMiniBar` のチップ実寸を
   `getBoundingClientRect()` で採り、**横スクロールに落ちない N の上限**を出す。
   ⭐ 計算上の予測 = `#hpMiniBar` は `gap:6px` / 左右 `padding` 6+6 / `.hpChip { flex:1 1 0; min-width:52px }`
   (`index.html:2088-2096`) なので、390px では
   **4 人 + 撤退 = 5 枚 → 70.8px / 5 人 + 撤退 = 6 枚 → 58.0px (収まる) / 6 人 + 撤退 = 7 枚 → 48.9px (溢れる)**。
   ⚠ **予測と実測が食い違ったら実測が正**。予測に合わせて assert を書き換えないこと。
7. **カメラ / 主人公が画面外のフレーム率**(本命) — 同一シナリオ・同一順序のペアで
   N=4 と N=5 を走らせ、desktop 1280x800 と compact 390x844 の**両方**で測る。
   ⭐ 比較の基準は `index.html:6343-6345` が残している既存の実測値
   (**compact 25.9%(廃坑) / 16.5%(竜の巣) / desktop 1280 = 0%**)。
   ⛔ **desktop が 0% から有意に上がったら、それが「5 人は行けない」の根拠**。
8. **カメラ / クランプ区間が空に落ちた率** — `computeCameraTarget` の
   `loCx <= hiCx` / `loCy <= hiCy` が偽になった回数を N ごとに数える。
   ⭐ 7. が「症状」で 8. が「原因」。**両方採ること**(症状だけだと直し方が決まらない)。
   ⚠ 計測は `window.__camAnchorOff` と同じ思想の**新規の dev シーム**で採る。本番は常に無効。
9. **置き去りと救済** — `MAX_LAG`(480) 超で `heroAI` が待った回数と、
   ワープ救済 (`index.html:16934`) の発動回数を N ごとに数える。
10. **描画コスト** — `performance.now()` で 1 フレームの実測を N ごとに採る。
    ⚠⚠ **JS 時間と真のコストは順位が正反対になることがある**(`project_camera_perf` の実測)。
    数字は出すが、**これ単独を可否の根拠にしない**。
11. **非退行** — 既存 golden が緑のまま:
    `verify_recruit_size` 79 / `driver_grid_p8` 55 / `driver_grid_p9` 52 / `driver_graph_p6` 244 /
    `driver_spawn_not_on_gate` 47 / `driver_encounter_mopup` 36。
    ⚠ `driver_grid_p8` の基準は **55/55**(`30f4869` で golden 更新漏れを回収済み)。
12. **報告** — 本依頼書へ「実装結果」節を足し、次を書く:
    - **5 人の可否 / 6 人の可否**(それぞれ ⭕ / ⛔ と、根拠になった受入条件の番号)
    - ⛔ の場合、**何を直せば行けるか**を箇条書き(見積りは不要。直す作業は別チケット)
    - 起草時の表(前提 4 点の判定)が実装後も正しかったか。**違っていたら本文を訂正する**

## 撤退スイッチ

⭐ **このチケットは「既定が撤退状態」**。`?party` を付けなければ本番と 1 ビットも変わらない
(受入条件 1. が機械的にそれを検査する)。

- `?party=N` … 調査シーム。**付けたときだけ**人数が変わる。N は 2〜8 の整数のみ。範囲外は無視 + `[DIAG]` 1 行。
- 計測用の dev シーム(受入条件 8. / 10. 用)は `window.__*` 側に置き、**本番は常に undefined**。
  URL からは有効化できないようにする(`index.html:6353` の `__camAnchorOff` と同じ作法)。
