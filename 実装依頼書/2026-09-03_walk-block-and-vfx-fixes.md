### 2-3. ⚠⚠⚠ **絵のピクセルからマスクを自動生成する規則は成立しない**(実測で棄却)

ユーザーが最初に選んだ「絵から自動で規則的に起こす」を、**現行の手書きマスクを教師にして
検算したところ不成立だった**。この節が 1 点目の方針を決めている。

現行マスク(n0 726 マス / n1 897 マス = 計 1623 マス)をラベルにして、各タイルセルの
特徴量が `#` と `.` をどれだけ分離できるかを AUC で測った。

| 絵 | 最良の特徴量 | **AUC** | 最良精度 | 混同(TP,FP,FN,TN) |
|---|---|---|---|---|
| n0 (blocked 321 / 726) | 暗部率 | **0.662** | 0.623 | 159, 112, 162, 293 |
| n1 (blocked 409 / 897) | 暗部率 | **0.685** | 0.671 | **375, 261, 34, 227** |

他の特徴量(平均輝度 / 彩度 / 輝度分散 / エッジ密度 / 明部率)はすべて **AUC 0.51〜0.65**。

- 実用の下限とされる **0.80 に遠く届かない**。最良でも **3 マスに 1 マス間違える**。
- n1 で暗部率を使うと、**床 488 マスのうち 261 マス(53%)を誤って塞ぐ**。
  塞がり率は 45.6% → **70.9%** に跳ね上がり、誤って塞いだ中に通路が含まれるため
  **ほぼ確実に到達不能が出る**。
- ⭐ **教師データの正しさは機械で検算済み**: スクリプトが数えた `#` の数(n0 = 321 / n1 = 409)が
  `probe_paint_overlay.js` の `tally.mask`(321 / 409)と一致した。
  ⚠ 最初の試行では n0 を 140 と数えており、この検算で**転記ミスに気づいて直した**。
  **「教師ラベルを別経路の実測と突き合わせる」を省くと、分析ごと嘘になる。**

**なぜ伸びないか** = §2-4 の**規則②**が「立体物か平置きか」の判別を要求しており、
これは色・明度・エッジのどれでも決まらないため。レールは暗く影もあるので床と区別が
つかず、明るい木箱は暗部率では拾えない。

⭐⭐⭐ **計画窓が目視で候補を挙げる場合も、同じ限界にぶつかる**。実際に 64px/タイルの

**「絵に木材が見えるが、それが立っているのか床に敷かれた板なのか」が判別できない**。
だから §4-1 は「候補を確定して流し込む」ではなく「**候補を人が指せる状態にし、
誤った候補が入っても壊れないことを機械が保証する**」という組み立てにしてある。

### 2-5. ⚠⚠⚠ 魔法陣がズレる真因 —— `zTf()` の前置 `scale` と `transform-origin` の衝突

**症状は camZ(ズーム)が 1 でないときだけ出る。** 陣は常に**右下**へ滑る。

`index.html:10721` が陣の位置をこう書いている:

    el.style.left = SX(wx) + "px";                     // wx = unit.x + size/2
    el.style.top  = SY(wy) + "px";                     // wy = unit.y + size*0.93
    el.style.transform = zTf("translate(-50%, -" + (S.anchorFY*100) + "%) scale(" + f.scale + ")");

`zTf` は camZ が 1 でないとき **`scale(camZ)` を左へ前置する**(`index.html:4162`):

    function zTf(inner) { return (camZ === 1) ? inner : ("scale(" + camZ + ") " + inner); }

そして `.fxCastCircle` の **`transform-origin` は `50% 64%`**(`index.html:739`)。
前置された `scale(camZ)` はこの origin 周りで効くので、楕円中心が

    ΔX = 0.5 * w * (1 - camZ)      ΔY = 0.64 * h * (1 - camZ)

だけ右下へ滑る。**実測(2026-09-03、術者 displaySize=96 → 陣 w=144.1 / h=90.1)**:

| camZ | 実測ズレ (px) | 予測 `0.5w(1-z)` / `0.64h(1-z)` | 一致 |
|---|---|---|---|
| **1** | (0.01, -0.01) | (0.00, 0.00) | ✅ **camZ=1 では正常** |
| 0.8125 | (13.52, 10.80) | (13.51, 10.81) | ✅ |
| 0.5 | (36.04, 28.81) | (36.03, 28.83) | ✅ |
| **0.25** | **(54.06, 43.23)** | (54.05, 43.24) | ✅ |

小数第 2 位まで一致(誤差 ≤ 0.02px)。⭐ camZ=0.25 のとき術者は画面上 24px なので、
**キャラ 2.2 個分右下**に出る = ユーザーの言う「離れた場所」。

⭐⭐⭐ **なぜ陣だけが壊れているか** —— `index.html:2901-2906` の CSS が設計の前提を書いている:

    /* 中央アンカー (margin で自分の半分だけ戻している) の絵は、既定の中心 origin のまま
       scale すれば中心が動かない。inline transform を持つものは JS 側 zTf() が合成する。 */
    body.zoomed .fxMissile, body.zoomed .fxArrow, body.zoomed .fxFireImpactCore { … }

つまり中央アンカーの VFX は **margin で中心合わせ**する前提。
**`.fxCastCircle` だけが `translate(-50%,-64%)` で中心合わせしており、これが例外。**

⭐ **プロジェクトはこの罠を既に知っている**。`index.html:2907-2909` が照準線について
**まったく同じ式**を書いて対処済み:

    /* 照準線は「起点から伸びる線」なので、軸を**起点 (左端中央)** に置く。
       ⚠ 既定の中心 origin のまま縮めると、長さ L の線が L(1-z)/2 だけ横へ滑る
       (6 タイル = 576 世界px の線なら z=0.25 で 216px のズレ)。 */

**魔法陣だけが取りこぼされていた。**

**camZ の値域**: `ZOOM_MIN = 0.25`〜`1`(`index.html:6706` / `:6771`)。
n1 は 39x23 の大部屋なので実プレイでは常に camZ < 1 = **常にズレている**。

### 2-7. ⚠⚠⚠ 既存 golden が緑のままな理由 —— ドライバが `camZ` を掛けていない

`tools/driver_cast_circle.js` は **53/53 で緑**なのに実機では壊れている。
原因はドライバ側の穴で、**実装とドライバが同じ間違いを共有している**:

    // tools/driver_cast_circle.js:311-314
    check('5.3 DOM の left/top はワールド座標 - カメラ',
          Math.abs(foot.left - (foot.probe.footWX - foot.camX)) < 0.51
          && Math.abs(foot.top - (foot.probe.footWY - foot.camY)) < 0.51, …);

`SX(wx) = (wx - camX) * camZ`(`index.html:4143`)なのに、**`* camZ` が無い**。
= この assert は **camZ=1 でしか成立せず、camZ≠1 を原理的に測れない**。

さらに `5.4` は `/translate\(-50%,\s*-64%\)/.test(foot.transform)` という**部分一致の正規表現**。

### 4-2. 魔法陣を術者の足元へ(2 点目)

**方針: `scale(camZ)` を translate の「左」ではなく「右」へ置く。**

平行移動は origin に依存しないので、`translate` を先に効かせてから `scale` すれば
楕円中心は `left/top` へ正しく着地し、しかも **scale の中心は origin(= 足元)のまま**なので
展開アニメが「足元から立ち上がる」性質も保たれる。

`index.html:4162` の隣に姉妹関数を足す(⛔ **`zTf` 自体は 1 バイトも変えない** —
`rotate` 用の 2 箇所が正しく動いている):

    /* 中心合わせを margin ではなく transform の translate でやる要素用。
     * ⚠ zTf() は scale を**前置**するので translate 量まで camZ 倍され、
     *   transform-origin 周りで楕円中心が 0.5w(1-camZ) だけ右下へ滑る (#46 §2-5)。
     *   こちらは scale を**後置**するのでズレない。camZ===1 では引数をそのまま返すので
     *   従来と 1 ビットも変わらない。 */
    function zTfAnchored(inner) { return (camZ === 1) ? inner : (inner + " scale(" + camZ + ")"); }

呼び口を 2 箇所だけ差し替える:

- `index.html:10721` … `zTf(...)` → `zTfAnchored(...)`
- `index.html:11234` … `zTf("translate(-50%, -50%)")` → `zTfAnchored("translate(-50%, -50%)")`

⛔ **動かしてはいけない値**: `CAST_CIRCLE_FOOT_FY = 0.93`、`anchorFY = 0.64`、
`.fxCastCircle` の `transform-origin: 50% 64%`、`castCircleDiameter()` の KNEE 式。
**ズレの原因は座標でも径でもなく transform の合成順序だけ**なので、他をいじると
camZ=1 での見た目まで動いて既存 golden が壊れる。

⭐ `body.zoomed .fxFireImpactCore { transform: scale(var(--camz,1)) }`(`index.html:2904`)は
**残す**。inline が勝つので今は死んでいるが、inline を書かない経路が将来できたときの保険。
