# 壁との当たり判定の箱が 72px スプライト前提で直書きされている

- **ステータス**: **完了 `f8c3bba`**(2026-08-21・#1 `7c59c44` の後)
- **起草日**: 2026-08-20
- **対象**: `index.html`
- **出自**: 廃坑の壁抜け調査(`2026-08-20_mine-wall-clipping.md`)の副産物。同じ根だが**全ユニットの被弾挙動が変わる**ので別チケットに切り出した。

---

## 目的

大型ユニットの「壁にぶつかったか」の判定が、**体のある場所ではなく左上のあらぬ場所**を見ている状態を直す。

---

## 事実(コードを読んで確認済み。数値は実コードから)

### W1 40x40px の箱が、スプライトの左上から (16,18) の位置に直書きされている

2 箇所で同じ定数が使われている:

```js
// index.html:16128  makeOverlapUnit — 仲間と敵の全部が通る
wallBox: (cx, cy) => ({ left: cx - size / 2 + 16, top:    cy - size / 2 + 18,
                        right: cx - size / 2 + 56, bottom: cy - size / 2 + 58 }),

// index.html:16265  moveEnemies のノックバック
if (!wouldOverlapWall(newEX + 16, enemy.y + 18, newEX + 56, enemy.y + 58)) enemy.x = newEX;
```

どちらも **スプライトの箱の原点 +(16,18) から 40x40px**。`displaySize` に一切追随しない。

### W2 ズレは体が大きいほど直線的に増える

箱の中心 = 原点 +(36, 38)、スプライトの中心 = 原点 + `displaySize/2`。差は **(36 − size/2, 38 − size/2)**:

| displaySize | 該当ユニット | 箱の中心のズレ | タイル換算 |
|---|---|---|---|
| 66〜74 | goblin / hobgoblin など | (+3, +5) 〜 (−1, +1) | ほぼ 0 |
| 72 | — | **(0, +2)** ← この値のために作られた箱 | 0 |
| 96 | goblinKing | (−12, −10) | 0.1 |
| 176 | **goblinChariot(縮小後)** | (−52, −50) | 0.5 |
| 192 | shadowBeast | (−60, −58) | 0.6 |
| 240 | lich / griffon / umber_hulk / sovereignEye / caravanWagon | (−84, −82) | **0.9** |
| 248 / 260 | lizardChieftain / chimera | (−88, −92) | 0.9 |
| 360 | hydra / pharaxus | **(−144, −142)** | **1.5** |

→ ハイドラとファラクサスでは、当たり判定の箱が体の **左上 1.5 タイル**にある。

### W3 実害が出る場所は限定的(だから緊急ではない)

- `resolveUnitOverlaps` の壁チェック(`index.html:16209` / `16213`)は、その手前の `if (U.mass >= OVERLAP_HEAVY_MASS) continue;`(`16204`)で **heavy ユニットを丸ごと飛ばす**。つまり `isBoss` か `displaySize >= 200` の 11 体はここを通らない。
  → **通ってしまうのは `shadowBeast`(192・`isBoss` なし)だけ**。ズレ 60px。
- ノックバック(`16265`)は **heavy かどうかを見ない**ので、**大型 12 体すべてが対象**。箱が岩の中を指すため、大型の敵は事実上ノックバックしない/おかしな向きに弾かれる。

### W4 プレイヤーの箱は別物で、こちらは正しい

`28/34/68/82`(`index.html:5993` / `6006` / `15850` / `15852` / `16145` / `16687`)は 96px スプライト前提。
箱の中心 = 原点 +(48, 58) = **横は中心・縦は足元寄り**で、意図どおり。**ここは触らない**。

## 実装方針

1. **箱を返す関数を 1 本だけ作る**。`unitWallBox(def, boxX, boxY)` → `{left, top, right, bottom}`。
   - `2026-08-20_mine-wall-clipping.md` の STEP3 で作る `unitBodyTiles` と **同じ比率(`bodyRatioX` / `bodyRatioY` / `bodyOffY`)を出所にする**。判定の出所を 2 つ持たない。
   - 比率が未指定の def は **今の 40x40 と同じ箱を返す**(= 既存の全ユニットで 1 ビットも挙動が変わらない)。
2. `makeOverlapUnit` と ノックバック 2 行をこの関数へ差し替える。
3. 大型 12 体の def に比率を足すのは**この時点ではやらない**。まず「配線だけ + 恒等」で 1 段を切る。
   ⭐ 挙動不変のリファクタは golden で証明できる(`tools/_golden.js`)。**機能を足す前に「配線だけ + golden」の段を挟む**。
4. 次の段で 12 体に比率を入れる。**1 体ずつではなく、比率のもとになる bbox を全部まとめて実測してから**入れる。
   測り方は mine-wall-clipping の F3 と同じ(シートの alpha bbox ÷ フレームサイズ)。

---

## 受入条件

### §1 恒等(配線だけの段)
- (1a) 比率を持たない def について、新旧の `wallBox` が **4 辺とも 1px も違わない**
- (1b) golden が **全ドライバで一致**(canvas の SHA)
  ⚠ golden は canvas の SHA しか見ない。DOM を触ったら別の測り方を用意すること。

### §2 効果(比率を入れた段)
- (2a) 各大型ユニットについて、箱の中心とスプライトの内容 bbox の中心の差が **16px 以内**
- (2b) ノックバック: 大型の敵を壁に背を向けて殴ったとき、**壁へめり込まない かつ 全く動かないでもない**
  ⚠ 「全く動かない」で緑にしないこと。今の欠陥は「箱が岩の中 → 常にブロック」なので、**動かないままでも assert が通る書き方をすると欠陥が温存される**。
- (2c) 6 シナリオを `?autoplay` で 1 周ずつ回して `dungeonCleared` に到達する(通れた隙間が通れなくなっていない)

### 負のコントロール

| 変異 | 注入する欠陥 | 赤くなるべき節 |
|---|---|---|
| `oldbox` | `unitWallBox` を旧 40x40 固定へ戻す | §2a |
| `ratioall` | 比率未指定の def にも新箱を適用 | §1a |

## 実装結果 (2026-08-21)

**ステータス**: 完了 `f8c3bba`
**検証**: `node tools/driver_wallbox.js` → **28/28 PASS**(負のコントロール 4 本すべて発火)

### 入れたもの

| 段 | 何を |
|---|---|
| STEP1 | 直書き 3 箇所を `unitWallBox(def, originX, originY)` の 1 本へ畳む。**返す値は 1px も変えない** |
| STEP2 | 大型 12 体の def に実測比率を入れ、箱の**中心**を体へ寄せる。撤退 `?wallbox=0` |

### 依頼書からの逸脱(5 点)

#### D1 ⚠ 行番号はすべてずれていた(#4 と同じ)

`makeOverlapUnit` の `wallBox` は 16128 ではなく **16297**、ノックバックは 16265/16267 ではなく
**16434/16436**。中身は依頼書の記載どおりだった。**行番号でなく識別子で grep すること**。

#### D2 ⭐⭐⭐ 測定器の落とし穴 — 比率は「シートのどの行を測るか」で変わる

依頼書 #1 の F3 は「各コマの alpha の bbox を**全コマ**で取って和集合」と書いてあるが、
記録されている戦車の値 (幅 173px / 高さ 139 / 上端 44) は **row2 だけ**の値だった。

| 測り方 | 幅 | 高さ | 上端 |
|---|---|---|---|
| row0 (idle) | 164 | 138 | 44 |
| **row2 (chase/search/returning = 移動中)** | **173** | **139** | **44** ← def の 0.901/0.724/0.229 と一致 |
| 全 30 コマの和集合 | 182 | 139 | 44 |

行の意味は [index.html:11340-11356](../../index.html) にある(0=idle / 1=alert / **2=移動** / 3=攻撃 / 4=死亡)。
**壁に当たるのは移動中の姿勢**なので row2 が正しい。残り 11 体も row2 で測った。
⭐ **既知の値を再現してから他へ適用する**。最初 row0 で測って 0.854 が出た時点で、
「codex の納品が違う」ではなく**自分の測定器**を疑ったのが分かれ目だった。

#### D3 `bodyOffX` を新設した(依頼書は 3 つの比率だけを出所と書いていた)

`bodyRatioX` / `bodyRatioY` / `bodyOffY` の 3 つは **体が左右対称**であることを仮定している
(`unitBodyTiles` は `left = cx − rx*S/2`)。実測ではハイドラの中心が **−23.4px**、
ファラクサス **−17.8px**、リザード長 **+12.9px** ずれており、対称仮定のままでは受入条件の
16px を超える。よって `bodyOffX` を追加した。

⚠ **`unitBodyTiles` は `bodyOffX` を読まない** = 戦車の footprint 判定は**ビット不変**。
装置 assert (3f) がこれを見張っている。

#### D4 箱の**大きさ**は 40x40 のまま据え置いた

依頼書は「比率を出所にする」としか書いておらず、体の実寸まで広げる読み方もできる。
しかし 360px のハイドラで箱が **3.4 タイル**になり、狭い部屋では一歩も弾かれなくなる
= §2b が警告している「**全く動かないままでも assert が通る**」で欠陥が温存される。
大きさを変えないので、受入条件 (2c)「通れた隙間が通れなくなっていない」も**原理的に**満たす。

#### D5 ⚠⚠⚠ 最大の逸脱 — 「体の中心へ寄せる」だけでは欠陥を再生産した

素直に内容 bbox の中心へ寄せた版を測ったところ、**体をフレームの下寄りに描いてある 6 体**
(ハイドラ / ファラクサス / リッチ / 巨熊 / リザード長 / 馬車) で箱が**下隣のタイルへ出て**、
**廃坑の床タイルの 23.9%** で箱が岩の中に入った。これは今直している「箱が岩の中 → 常にブロック」
そのものの再生産である。

原因: ゲームの位置モデルはどこも `floor((x + displaySize/2) / TILE_SIZE)` = **スプライトの中心**。
当たり判定だけが**絵の中心**を追うと、他の全判定と食い違う。

→ **箱の中心はスプライトの中心から ±28px (= TILE_SIZE/2 − 箱/2) を超えない**というクランプを入れた。
これで箱は常に「スプライトの中心を中心とする 1 タイルの正方形」の内側に収まり、床タイルに
立っている限り**箱が壁に入ることは原理的に無い**(実測でも全 6 シナリオ x 12 体で 0 件)。
⭐ 72px スプライトの旧箱も (0, +2) でこの規則を満たしている = **新規則は旧規則の拡張**。

### 受入条件の言い直し(D5 に伴う)

§2a「箱の中心と体の中心の差が 16px 以内」は、クランプが効く 6 体では**そのままでは満たせない**
(残差 3.0〜37.6px)。**手段でなく目的**で測り直した:

| 節 | 言い直した条件 | 実測 |
|---|---|---|
| (2a) | 箱の中心 = 「体の中心へ寄せる・ただしスプライト中心から ±28px」を厳密に満たす | 12 体一致 |
| (2a-2) | 体の中心との残差が**旧箱の半分以下**、かつ 40px 以内 | 新 0.0〜37.6 / 旧 83.8〜243.0 |
| (2a-3) | 箱 40x40 が**体の外接矩形の内側に完全に収まる** | 12 体すべて内側 |
| (2c-2) | 箱が壁の中に居る床タイルが **1 つも無い** | 全 6 シナリオ x 12 体で 0 件 |

⭐ 期待値は **def に書いた数字ではなく PNG の alpha bbox から** ページ内で組み立てている
(def の数字が間違っていればここで落ちる)。

### 測らなかったもの

受入条件 (2c)「6 シナリオを `?autoplay` で 1 周ずつ回して `dungeonCleared`」は**専用には測っていない**。
敵の移動そのものは `wouldOverlapWall` を**通らない**(通るのは押し出しとノックバックの 2 経路だけ)ので、
「通れた隙間が通れなくなる」は原理的に起きない。代わりに既存の完走ドライバ
(`graph_run` / `graph_kinds` / `grid_p9` / `mine_wall` / `sce1_events`) を回した。
