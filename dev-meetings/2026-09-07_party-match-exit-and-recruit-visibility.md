# 開発会議〔第1段：候補出し〕：マッチング画面の出口と「同行の約束」の可視化

**議題**: パーティ・マッチング画面（`#partyMatchOverlay`）から酒場へ戻れない / 「募集をかけ直す」が効かない / 酒場で誰と約束したか分からない、の 3 点。
**ゴール**: 毛色の違う実装候補を出して、進む方向を 1 つ選ぶ

## 0. 会議前の実測（⚠ 議題の主張を本番コードで 1 つずつ測った）

| # | ユーザーの主張 | 実測 | 判定 |
|---|---|---|---|
| 1 | マッチング画面から酒場へ戻れない | 閉じる口は **`#pmDepart` ただ 1 つ**（`tavern.html:8544` に明記）。通常経路（受注直後）はラベル「出発する」= 押すと潜る。`review` モードだけ「準備へ戻る」だが、その準備画面は **#55 で廃止済** | ✅ **主張どおり** |
| 2 | 「募集をかけ直す」が機能していない | ボタンは **配線されている**（`click`+`touchend` 両方 → `doRecruitReroll()`）。真因は `regeneratePartyMembers()`（`tavern.html:6441`）が #54 の `isRecruitTalkOn()`（既定 ON）で**早期 return** し、`DFRecruits.all()` をそのまま組み直すだけ = **再抽選が 1 行も走らない** | ⚠ **主張は正しいが真因が違う**。壊れたのではなく **#54 で意味を失った** |
| 3 | 酒場で仲間にしてる人間が分かるようにしてほしい | ★ **#57 で実装済み**。`patronLabelPaint()`（`tavern.html:7837`）が約束済みの頭上札へ **「🤝 」を前置**、`refreshPatronLabelFor()` で付け外しも即反映 | ❌ **主張が崩れた（既に出荷済み）** |

**⇒ 議題 3 の本当の問題は「未実装」ではない。** 届いていない理由の候補:

- ⚠ 札が出るのは **卓の 4 席（`todaysPatrons`）だけ**（`tavern.html:9759` — 店主 / 酔漢 / 給仕 / 荷運びには出さない）
- ⚠ 札の文字は **12px（compact 11px）**。**#57 の実機体感 ①「頭上札の 12px が読めるか」は未消化のまま**
- ⚠ **一覧で確認する口が無い** — 「今 3 人のうち誰と約束したか」は札を 1 枚ずつ見に行くしかない

**その他の実測**: `RECRUIT_MAX = 3` / `DFRecruits` の API は `all / add / remove / has / count / **clear**` が揃っている（= 解散の実体は既にある）/ 帰還時に `DFRecruits.clear()` が既に走る（`tavern.html:5312`）。

## 第1ラウンド：ブレスト（各専門領域から方向性を 1 つ）

【ガイウス】いいか、まず枠付けからだ。この画面は「募集に応じた者が名乗りを上げる場」だろう。**そこに出口が無いのは、酒場の扉に鍵を掛けているのと同じだ。** Gold Box では受けた依頼を保留して街に戻る自由が必ずあった。私は「酒場へ戻る」を単なる画面の閉じるボタンではなく、**依頼を一旦降りて出直す**という体験にしたい。冒険者は依頼を選ぶ側だ。

【レンツ】待った、ガイウス。それは規模が跳ねる。俺の方向性は**もっと地味だが確実な方**だ ——「口の意味論を正す」。実測のとおり `doRecruitReroll()` は **#54 の日に死んでいる**。押しても `DFRecruits.all()` を組み直すだけで顔ぶれは絶対に変わらない。ボタンが嘘をついている状態だ。**`DFRecruits.clear()` はもう存在する**から、「募集をかけ直す」を「約束を解散する」へ差し替えるのは実質 1 本の付け替えで済む。工数で言えば最小。

【ミサキ】私は見た目から。🤝 が付いてるって言われても、**12px の札の頭に絵文字 1 個**でしょ? それ、iPhone で気付ける自信ある? 私なら**席そのものを変える**。約束した相手の足元に金の輪……あ、ごめん、それ #57 でホールド・パーソンに使った奴だ。じゃあ**札の色を変える**。約束済みだけ枠を金にして背景を濃くする。あと**マッチング画面のカードに「酒場で声を掛けた」出自を出したい**。今のカードは自動抽選の頃と見た目が同じで、**自分が選んだ実感がゼロ**なの。

【ノエル】辛口でいくよ。3 つとも**同じ 1 個の欠陥の枝**だと思う ——「**同行の約束という状態が、どこにも一覧されていない**」。マッチング画面に出口が無いのも、解散の口が無いのも、誰と約束したか分からないのも、全部そこ。私の方向性は「**酒場に常設の『同行の約束 N/3』パネルを置く**」。誰と約束してるか一覧して、その場で個別に解除できる。マッチング画面の「戻る」もそこへ着地させればいい。……あと言っておくけど、**overlay には iOS の戻るジェスチャも効かない**。今の状態は「受注したら潜るしかない」= 詰みの一歩手前だからね。

## 第2ラウンド：絞り込み（制約で間引く）

【レンツ】ガイウスの「依頼を降りる」は筋は通ってるが、**受注状態の巻き戻しが要る**。`prepScenario` だけじゃない —— **事前情報の使用済みフラグ（`prepIntelUsed` / `prepIntelSuccess`）をどう戻すか**が問題だ。戻さなければ「戻る→再受注」で情報だけ食い逃げできるし、戻せば「3 回振り直し放題」になる。どちらもバランスに穴が開く。**これは単独チケットの規模だ。**

【ガイウス】……む。確かに、吟味と聞き込みと祈りを引き直せてしまうのは D&D として下品だな。だが「出口が無い」を放置するのはもっと悪い。**ならば折衷だ** —— 戻るときに**事前情報の使用済みは持ち越す**。降りても下調べの記憶は残る。それが自然だろう。

【ノエル】それなら通る。でも**降りた依頼が掲示板から消えるのか残るのか**は決めないと、実機で必ず事故る。……ミサキの「席を光らせる」は反対。**#57 の金の輪の光量がまだ実機で確認できてない**の。光ってる物を増やす前に、既にある光を確かめるのが先。

【ミサキ】ぐっ。……分かった、光り物は引っ込める。でも**札の色分けは譲らない**。CSS 1 行の話だし、12px のまま絵文字だけで区別させるのは無理がある。

【レンツ】色分けは賛成だ。**`.patronLabel` に `.promised` クラスを足すだけ**なら CSS + `patronLabelPaint` の 1 行で済む。⛔ ただし**札を出す場所を増やすのは駄目**だ。`todaysPatrons` の 4 席に限っているのは #57 の設計で、店主や給仕に札を出すと「声を掛けられる相手」の見分けが逆に壊れる。

【ノエル】もう 1 つ潰しておく。**「募集をかけ直す」を本当に機能させる**（= `DFRecruits` を無視して自動抽選へ戻す）案。これは**却下**。#54 が「誰も誘っていなければソロ」まで踏み込んで「誘う意味」を作ったのに、引き直せたら**声を掛ける行為が無意味に戻る**。依頼書 §6-4 が名指しで禁じてる。

【ガイウス】異論なし。あのボタンは**役目を終えている**。残すなら別の役目を与えるしかない。

【レンツ】最後に工数の見立てを。**今回は `tavern.html` 単独**で、`index.html` との二重同期は要らない。`DFRecruits` は既に `js/recruit-candidates.js` に切り出してあるから、解散も一覧も**新規ロジックはほぼゼロ**。**ここは安い。** 高いのはガイウスの「依頼を降りる」だけだ。

# 🎲 実装候補（方向性を選んでください）

## 候補①：口の意味を正す — 「酒場へ戻る」と「約束を解散する」

- **ざっくり規模**: **小**

## 候補②：「同行の約束」を一覧できる常設パネル

- **ざっくり規模**: **中**

## 候補③：🤝 を「見て分かる」強さへ
- **ジャンル**: ビジュアル / 演出
- **狙い**: 約束済みの札を色・枠で明確化＋マッチング画面のカードに「酒場で声を掛けた」出自を出す
- **ざっくり規模**: **小〜中**
- **既存流用度**: 高（`.patronLabel` に `.promised` を足すだけ。⛔ 札を出す席は増やさない）

- **ざっくり規模**: **中〜大**
- **既存流用度**: 中（受注状態の巻き戻しが新規。**事前情報の使用済みフラグの扱いが設計の山場**）

- **推し**: ガイウス ／ **慎重**: レンツ（情報の食い逃げ or 振り直し放題の穴が開く）

## 第1ラウンド：設計（レンツが実装アーキテクチャを出す）

【レンツ】着手前に測ってきた。**「閉じるだけ」で実装すると、その場で潜る。** これが最大の山場だ。

```js

await playPartyMatchCinematic(sc);        // ← 演出。閉じると resolve
if (PREP_SKIP_ON) { departToScenario(); return; }   // ⭐ #55 の 1 行。無条件で出発
```

【レンツ】……`prepIntelUsed` と `prepIntelSuccess` を**リセットする**（`tavern.html:6026-6027`）。**吟味・聞き込み・祈りが無限に引き直せる。** 候補④を採らなくても、①だけでこの穴が開く。

【ノエル】出目が気に入らなければ戻って引き直す、が最適解になっちゃうね。それは壊れてる。

【レンツ】救いはある。**`openPartyMatchReview()` が既にある**（`tavern.html:8606`）。`prepScenario` を使い回して `openPrep` を**通らずに**演出だけ開き直す関数だ。しかも review モードは `departToScenario()` を呼ばない（fire-and-forget）。**再入場はこれ一本**でいい。

【ガイウス】ならば置き場は決まりだ。**その口を候補②の常設パネルに持たせる。** ①と②が噛み合った。今まで `btnPartyView`（編成を見る）は #55 で廃止された準備画面の中にあって、**誰にも押せなくなっていた**わけだな。

## 第2ラウンド：肉付けと衝突

【ミサキ】カードの出自バッジ、やらせて。今のカード、**自動抽選だった頃と見た目が 1 ミリも変わってない**の。自分で酒場を歩いて声を掛けた 3 人が並んでるのに、くじで引いた人と同じ顔で出てくる。そこに「🤝 酒場で声を掛けた」の小さな一行があるだけで、**画面の意味が変わる**。

【レンツ】同じ日の卓に同名が 2 人座る確率は低い。**許容してコメントに残す**でいい。⛔ ここで名簿の同一性システムを作り始めたら規模が跳ねる。

【ノエル】そこは私も譲らない。**常設は「🤝 3/3」のバッジ 1 個だけ**。押すと一覧が開く。開いた中に「誰と誰」と「個別に解除」と「編成を見る」を入れる。⚠ **#56 で引き出しが潰れた前科がある**から、開いた中身は必ずスクロールする器に……いや待って、**#56 の真犯人は `overflow-y:auto` そのものだった**（それを持つ flex 子は自動最小サイズが 0 になって収縮を全部吸う）。**同じ轍を踏まないよう、パネルは flex 子にしない。**

【ガイウス】解散は破壊的だぞ。3 人まとめて消える。確認は要るか?

【ノエル】要る。でも**新しいダイアログは作らないで**。……ただ、救いがあるの。解散したらソロになるでしょ? **#54 の単身出発の警告（`needsSoloWarning`）が既にある。** 解散 → 出発 で「一人で行くのか?」が必ず出る。**安全網はもう張ってある**から、解散側の確認は 1 枚で十分。

【ミサキ】札の色分けは? 私は約束済みだけ枠を金にしたい。

【ノエル】⚠ 待って。**#57 の実機体感 ①「頭上札の 12px が読めるか」がまだ未消化**なの。読めないのが原因なら、色を変えても読めない。……でも色分け自体は CSS 1 行だし、**入れて損はない**。順序としては「**色分けは入れる・サイズは実機を見てから決める**」で。⛔ サイズを今この場で決め打ちしない。

【レンツ】まとめる。**今回は `tavern.html` 単独**。`index.html` との二重同期は要らない。`DFRecruits` は `js/recruit-candidates.js` に切り出し済みで `all/add/remove/has/count/clear` が揃っている ⇒ **新規ロジックはほぼゼロ**。高いのは**演出 promise の記名化**だけで、それも 3 箇所の `resolve()` を触るだけだ。

## STEP1：演出 promise の記名化 + 「🍺 酒場へ戻る」【候補①・山場】

## STEP5：受入ドライバ（port **10140**）

**素で通す条件**（抜粋）
- (1a) 受注 → マッチング画面に **「酒場へ戻る」が見える**
- (1b) ⭐⭐⭐ **戻るを押しても `departToScenario()` が呼ばれない**（= 潜らない）。**本件の中核**
- (1c) 出発するを押すと**従来どおり潜る**（非退行）
- (1d) `?pmback=0` で戻るボタンが**出ず**、出発は従来どおり
- (2a) 解散を押すと `DFRecruits.count()` が **0**、カード列が主人公 1 枚になる
- (3a) ⭐⭐⭐ **戻る → 「編成を見る」で再入場したとき `prepIntelUsed` が保持される**（引き直せない）
- (3b) 未受注では「編成を見る」が出ない
- (4a) 約束済みの席の札にだけ `.promised` が付く。⛔ 4 席以外に札が増えていない

**変異（負のコントロール）** — ⚠ 「注入できたか」でなく**測っている場所に現れるか**まで設計する
- M1: 早期 return を "back" にする → **(1c) が赤くなること**（#55 の出発が死ぬ罠の検出器）
- M2: 再入場を `openPrep` 経由に戻す → **(3a) が赤くなること**
- M3: `resolve()` を無記名に戻す → (1b) が赤
- M4: 札を全 NPC に出す → (4a) が赤
- M5: 解散で `clear()` を呼ばない → (2a) が赤

⚠⚠⚠ **#58 の教訓を必ず適用**: 「**門番が例外扱いする対象を、門番の下流で測ってはいけない**」。本件の門番は `PREP_SKIP_ON` と `isRecruitTalkOn()` の 2 つ。受入条件をこの 2 つの**下流**に置くと、永久緑になる。
